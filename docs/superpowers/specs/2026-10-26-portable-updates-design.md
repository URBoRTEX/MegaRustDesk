# MegaRustDesk: обновления portable-клиента через GitHub

Дата: 2026-10-26. Статус: согласована владельцем, реализация разрешена.
Публичный репозиторий: `URBoRTEX/MegaRustDesk` — выбран владельцем.
Первый клиент с updater: отдельная версия после 0.2.3.

## Результат для пользователя

На обоих ПК работает одно portable-приложение. В главном окне видна его версия и кнопка
«Проверить обновления». При наличии нового релиза появляется «Обновить до …».
Приложение само скачивает проверенный пакет, заменяет файлы и перезапускается.
Пользователь больше не передаёт ZIP после каждого исправления.

Существующие 0.2.x не содержат этого механизма: один раз потребуется запустить новый
клиент. На втором ПК это выполняет человек, либо обновление доставляется через уже
разрешённый работающий удалённый сеанс. Скрытая установка, служба и автозапуск не нужны.
Обновление принимающего ПК нажимают на принимающем ПК. Кнопка на первом ПК обновляет
именно первый ПК; массового push-обновления других устройств в первой версии нет.

Встроенный чат, App Server и runtime Codex остаются исключены. Внешний Codex CLI/MCP
подключается по прежнему стабильному пути `RustDesk-Agent.exe --agent-mcp`.

## Проверенные исходные факты

- Основа — официальный RustDesk 1.4.3, Sciter/inline, Rust 1.75.0, Windows x64.
- `src/agent/portable.rs` задаёт APP_NAME=RustDeskAgent и каталог `data` рядом с EXE.
- Код upstream updater ведёт в установку и не подходит portable-сборке.
- GUI работает в Windows job с KILL_ON_JOB_CLOSE. Обычный дочерний updater погибнет
  при выходе GUI. Внешние процессы `--agent-mcp` находятся вне этого job.
- Закрытие viewer кнопкой X сворачивает его. Для замены файлов нужен настоящий выход.
- На первом ПК могут работать MCP-процессы других чатов. Их нельзя принудительно убивать.
- Текущий origin указывает на rustdesk/rustdesk, а не на репозиторий владельца.
- Пакет 0.2.3 был впоследствии заменён ZIP размером 167 020 638 байт: executable совпадал
  с 0.2.3, но архив дополнительно содержал старый runtime и локальную `data`.
  Значит, размер 150+ МБ сам по себе не доказывает старый EXE; обнаружена ошибка поставки.
  Попадание чужой `data` на второй ПК могло перенести настройки окна и изменить ID.
- Повреждённая поставка сохранена вне release в `.agent-build/quarantine`, не публикуется.
  Из проверенного staging восстановлен ZIP 17 607 331 байт без data/runtime; hashes и
  portable self-test в двух путях прошли. Пользовательские данные не изменялись.

## Подходы и решение

1. **Публичный GitHub + Releases — выбранный вариант.** Код, спецификация, история
   исправлений и инструкции находятся в репозитории, бинарные пакеты — в Releases.
   Клиент читает публичные релизы без аккаунта и без встроенного GitHub token.
2. Приватный GitHub потребовал бы отдельной выдачи доступа каждому клиенту. Владелец
   выбрал публичный вариант; приватная схема не реализуется.
3. Собственный update-сервер добавляет отдельную инфраструктуру. Для первой версии
   используем публичные релизы GitHub, без дополнительного серверного приложения.

Репозиторий должен содержать полный доступный соответствующий исходный код форка,
точный upstream base, lockfiles, инструкции и patch подмодуля hbb_common.
Локальные настройки, data, журналы, ключи, screenshots и generated build-каталоги
не входят в Git или опубликованные assets. Публикация выполняется по явному списку.

## UX и состояния

Место — компактный блок версии/обновления в главном окне, не новая панель чата.
Используются существующие `.button`, `.outline`, шрифты, отступы и color tokens.

| Состояние | Отображение и действие |
|---|---|
| idle | Текущая версия и «Проверить обновления» |
| checking | «Проверяю обновления…», повторный запрос заблокирован |
| current | «Установлена последняя версия» |
| available | Номер новой версии, краткое описание, «Обновить до …» |
| downloading | Прогресс загрузки; текущая версия продолжает работать |
| verifying | «Проверяю пакет…» |
| blocked | Понятное условие: завершить удалённые сеансы или закрыть внешний Codex |
| ready | «Перезапустить и обновить»; действие выполняет человек |
| applying | Закрытие приложения и работа отдельного helper |
| updated | Новый запуск показывает новую версию и подтверждение |
| failed | Текущая версия сохранена; сообщение и возможность повторить |
| rolled_back | Восстановлена предыдущая версия; причина сохранена локально |

Нет обязательной автоматической проверки при каждом кадре/клике, тихой установки
посреди работы или отдельного GitHub login в клиенте. Проверка обновлений — по кнопке.
Первый публичный клиент может быть prerelease; stable-канал не устанавливает prerelease.

## Формат релиза и доверие

Одна версия продукта хранится в одном исходном файле. Upstream version 1.4.3 остаётся
отдельным полем. Версия в UI, CLI, manifest, теге и названии asset должна совпадать.

Assets одного релиза:

- `MegaRustDesk-VERSION-windows-x64.zip` — только разрешённый portable payload;
- подписанный update manifest и Ed25519 signature;
- `SHA256SUMS.txt`;
- corresponding-source archive с изменённым hbb_common и build-инструкциями.

Manifest включает schema/product/platform/version/tag/repository, source commit,
sourceBuildId, asset name/URL/size/SHA-256 и точный inventory файлов с SHA-256.
Подпись проверяется над точными байтами manifest, до разбора доверенных полей.
В клиент встроен публичный ключ подписи. Закрытый ключ хранится вне Git и release,
локально защищён Windows DPAPI; начальный выпуск подписывается локально.
CI signing secret не создаётся без отдельного согласованного шага.

SHA-256 из того же скачанного JSON не является заменой подписи. Ошибка подписи,
неизвестный schema/platform/product/repo, downgrade или несовпадение version/tag
запрещают установку. Ключ нельзя заменить значением из скачанного manifest.
Плановая ротация ключа требует релиза, подписанного уже доверенным ключом.

GitHub API используется только для поиска опубликованного stable release. Далее
скачиваются фиксированные assets этого versioned release. Разрешён HTTPS и только
ожидаемые GitHub/CDN hosts; переход на HTTP и произвольные hosts запрещён.
Нельзя отключать проверку TLS или писать access-bearing redirect URL в журнал.
Таймаут, лимит API, отсутствие stable release и отсутствие интернета отображаются отдельно.

Релиз сначала собирается как draft; все assets проверяются до публикации. Assets
опубликованной версии не перезаписываются. Где доступно — immutable releases.

## Валидация пакета

Проверяются размер download и SHA-256, затем inventory. До извлечения запрещены:

- `data`, runtime Codex, auth/config/history/log/screenshot files;
- абсолютные пути, `..`, drive/UNC/ADS paths, reserved Windows names;
- links, повторные ZIP names и collisions без учёта регистра;
- неожиданные EXE/DLL/скрипты и любые файлы вне подписанного inventory;
- чрезмерные размеры отдельных файлов, общего распакованного payload и число entries.

Manifest не может сам разрешить запись в data. Разрешённые корневые файлы и каталог
licenses дополнительно ограничены клиентом. Update package извлекается только в
принадлежащий этому приложению staging; существующие чужие каталоги не очищаются.
Для публикации выполняется та же строгая проверка готового ZIP, а не только staging.
Рекурсивное архивирование запущенной папки приложения запрещено.

## Применение на Windows

1. Проверить writable portable-папку, свободное место и отсутствие другой транзакции.
2. Скачать, проверить и подготовить payload; текущий EXE пока не заменяется.
3. Не применять обновление при активных входящих/исходящих сеансах. Человеку нужно
   завершить их штатно, чтобы не потерять работу и не продолжать действия после разрыва.
4. Проверить процессы именно этой portable-папки. Внешний Codex не завершается.
   В первой версии при оставшихся внешних MCP-процессах установка блокируется с
   понятным сообщением: нужно завершить использующие клиент Codex/MCP-клиенты.
   Не использовать taskkill по одному имени и не останавливать чужие задачи.
5. Скопировать проверенный updater runner в отдельный рабочий путь, где он не удержит
   заменяемый EXE/Sciter. Early CLI dispatch helper — до agent::initialize/load Sciter/job.
6. Разрешить breakaway только в собственном GUI job и запустить helper через
   CREATE_BREAKAWAY_FROM_JOB. Сначала дождаться handshake helper, затем закрыть GUI.
   Проверить child HANDLE относительно собственного job до разрешения закрыть GUI;
   query должен подтвердить отсутствие child в этом job. Внешние job сохраняются:
   helper может остаться в них. Ошибка spawn/query или child в собственном job — отказ.
   Recovery до создания собственного job не запрашивает выход из внешнего job.
7. Helper ждёт завершения exact PID с проверкой времени создания/пути; pid reuse не
   должен приводить к завершению чужого процесса. Принудительного широкого убийства нет.
8. Сохранить предыдущий payload, вести журнал замен. Заменять только подписанные файлы.
   `data` не читать, не переносить и не заменять. Стабильный путь EXE и APP_NAME сохраняются.
9. Запустить новый клиент, проверить продуктовую версию/health marker. При отказе,
   locked file, истечении ожидания или неполной замене — вернуть прежний payload.
10. После успешного старта оставить current + один rollback; лишний собственный staging
    убрать по BUILD_RETENTION с точными путями, проверками использования и квитанцией.

Ни registry install, ни служба, ни драйвер, ни автозапуск, ни новые firewall rules
не добавляются. Задачи и авторизация внешнего Codex не изменяются.

## Репозиторий и выпуск

Публикуется отдельный публичный форк `URBoRTEX/MegaRustDesk`; upstream origin не
переписывается и в rustdesk/rustdesk ничего не отправляется. История/provenance
upstream и AGPL notices сохраняются. Изменения форка публикуются отдельной веткой.
Ненужные upstream workflows не запускаются при первой публикации.

Начальный поддерживаемый producer — существующая локальная Windows-сборка с pinned
inputs и автоматическими checks, затем локальная подпись и draft release upload.
Проверка готового архива обязательна непосредственно перед upload.

GitHub-hosted CI build — следующий воспроизводимый producer после bootstrap toolchain:
нынешний build.ps1 зависит от локального C:/CodexMaintenance и заполненного toolchain.
Нельзя объявлять CI настроенным, просто добавив YAML, который без этих путей не работает.
Workflow publication может принимать уже проверенные и подписанные assets; сам клиент
от способа сборки не зависит. Ключ подписи не передаётся build/PR job.

## Проверки и критерии приёмки

- Отрицательные crypto/manifest cases: неверная подпись/key/version/repo/hash/size,
  downgrade, prerelease в stable, malformed JSON и несовпадение tag/version.
- Реальные ZIP cases: contamination data/runtime, traversal, duplicates/case collisions,
  symlink/ADS/reserved names, extra payload, over-limit и повреждённый файл.
- Apply: locked file, отсутствующий runner handshake, job breakaway failure, отказ
  нового запуска, rollback, повторный запуск после незавершённой транзакции.
- Happy path: проверенный 0.2.3 → новый signed payload в task-owned QA; одинаковые
  data hashes/метаданные, стабильный EXE path, новая версия после запуска.
- Существующие gate/transport/identity tests и portable self-test продолжают проходить.
- UI: native Sciter light/dark, 1280×800 и 900×600, все состояния кнопки, недоступная
  сеть, активный сеанс, соседние соединение/пароль/MCP; никаких новых UI primitives.
- Browser gate фиксируется отдельно: Sciter/TIS не исполняется обычным браузером.
  Без нужного browser evidence итог UI остаётся «не проверено» по UI_CONTRACT.
- Реальная загрузка public release, подпись и применение на QA; второй ПК — после
  единственного bootstrap и подтверждения его актуального ID/разрешения человеком.

Подпись и успешная компиляция не означают полной portable-приёмки. В manifest/отчёте
раздельно: packageVerified, updateFlowVerified, nativeUiVerified, browserUiVerified,
realSecondPcUpdated, buildVerified и cleanupCompleted.

## Открытые пункты до выпуска

- Первичное состояние второго ПК: окно не видно, актуальный ID пока не подтверждён;
  неизвестно, затёрла ли распаковка большого ZIP его прежнюю data.
- Полный GitHub-hosted build требует отдельного bootstrap; локальный producer доступен.
- Прежние generated остатки имеют отказ автоматической очистки; обходить его нельзя.
- Quarantine с локальной data не является релизом и не публикуется/не удаляется как кэш.
